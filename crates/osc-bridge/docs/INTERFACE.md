# osc-bridge (application) — interface

**Langage** : cargo

The application offers three published surfaces: its command line, its MCP tools, and its OSC addresses. Each is a contract with people, agents and software outside the repository; a change to one goes up to the owner.

## The command line

| Command | Receives | Returns |
|---|---|---|
| `list` | — | the MIDI ports |
| `detect` | `--no-probe`; `--devices-dir`; `--consent <port>` (repeatable; refused with `--read`); `--learn` and `--listen-ms` (1000-30000, default 5000, only with `--learn`); `--share-fingerprint <port>` with `--vendor`, `--model` and `--firmware` (only with `--learn`); `--write <file>`; `--read <file>` | the devices recognised on the ports; with `--learn`, the notice (it listens N seconds, move the controls), then per device (all its ports) its fingerprint and the measures beside it; with `--write`, the same report and a capture file; with `--read`, the report over a capture, with no device and nothing sent (it refuses `--no-probe` and `--write`) |
| `run` | a driver, ports, OSC and WebSocket addresses, OSCQuery | a bridge for one device |
| `orchestrate` | a `bridge.toml` | several devices with routes between them |
| `mcp` | `--offline`, `--devices-dir` | the MCP server |
| `connect` | the relay address, private ports | a relay door |
| `export` | `--device` (a driver) and either `--format` (any format of `osd-formats`; an unknown name lists them), or `--on` (the target device, a driver file, id or slug) with `--yes` | the exported file on the standard output; with `--on`, the export put on the plugged target by the way its descriptor declares, or, without `--yes`, what would be written (nothing is sent) |
| `backup`, `restore` | `--device` (required: a driver file, id or slug), ports, a `.syx` file; `restore` also `--bank` and `--number` for a sound that carries no place | a dump taken (the sounds the driver recognises, on any channel) or sent (the driver's pauses; a bank it says cannot be written refused before any message; channel and device number written as configured) |
| `privacy` | `--offline`, `--private`, `--public` | the installation's settings |
| `inspect`, `lint` | a driver | its summary, its warnings |
| `osc-send`, `osc-listen` | an address and arguments, a bind address | one OSC message, the messages received |

### The detection capture

`detect --write <file>` writes what the detection observed, raw, as JSON (`format_version` 2; a capture of another version is refused with an error naming it, and a version 1 capture asks to capture again): `outputs` and `inputs` (the port names as the system gave them, in order), `cards` (the text of `/proc/asound/cards`), `usbids` (`card`, `text` of each card's `usbid`), `clients` (the text of `/proc/asound/seq/clients`, raw; empty where the system gives none: Windows and macOS read none today), `requests` (`port`, `bytes`) and `received` (`port`, `bytes`, `ms` since the first request). The pairing of inputs with outputs, the USB ids and the kind of each port are never written: `--read` derives them again, through the derivation the scan uses. The kind of a port (`client_kind` of each device of the report: `kernel`, a device of the system; `user`, a program; `unknown`) is the one entry of `clients` that has the port's client number and a client name equal to the port's (or to it once one final ` (digits)` is removed); the first word in brackets of the entry decides (`[User Legacy]` is `user`, `[Kernel …]` is `kernel`, any other word `unknown`); no entry, several, or no list gives `unknown`, and the port is matched as before. A port of kind `user` keeps only the candidates whose card, found by its id in the local catalogue, is of software kind: any other candidate (a card not known locally, or of hardware kind) and any `unlisted` entry is dropped, whatever the service answers, and the port is then unknown. `detect`, the learn mode and `detect_hardware` apply the same filter; the published form of their results gains no field. Only `/proc/asound/cards`, `/proc/asound/seq/clients` and each card's `usbid` (maker:product) are read; every other file of a card, the USB serial field, the host name and the user name are left out. The messages received are kept raw, not redacted, because the replay depends on them: a maker's reply may carry a serial number, so the person reads a capture before sharing it. The option writes a local file and sends nothing more than the detection does. The corpus of captures is `crates/osc-bridge/tests/fixtures/captures/`: one capture per bench session named by day, beside `<day>.expected.json` (port → device id, written by a person).

## The relay frames

`crate::synthub::relay_protocol` publishes the frames of the relay door, one contract with the service, whose browser door reads the same reference frames (`tests/fixtures/relay_frames.json`):

- built: `ports_frame(outputs, inputs)`, `share_frame(enabled, private)`, `midi_in_frame(port, data)`, `confirm_reply_frame(id, accepted)`, each a JSON value;
- read: `parse_door_frame(text)` gives a `ServerFrame` (`Hello`, `MidiOut`, `Confirm`, `ConfirmCancel`, `Paired`, `Error`) or nothing for text that is not a known frame;
- the rule `needs_confirmation` and `is_identity_request` on a message.

## The MCP tools

`send` always asks for the acknowledgement and hands back at the first answer: `/bridge/done` gives `sent: true`; `/bridge/fault` gives `isError: true` with the address and the reason, in text and in `structuredContent` (`sent: false`, `address`, `reason`); when nothing answers within 3 s (a guard, not a delay) it gives an error saying osc-bridge does not answer at that address.

The tools are described once, from Rust types; the list the server offers is generated from them and compared, at each change, with the published list. Local tools work offline; the others are the service's, forwarded through `synthhub-protocol`.

`detect_hardware` takes `learn` (boolean) and `listen_ms` (1000-30000, default 5000; a value outside is refused with an error naming the range). In learn mode it matches no driver: it listens for that time on each port, sends nothing but the universal Identity Request (on every output of a device), says in its text that it listens N seconds and that the person can move the controls, and returns one element per device (the ports sharing an ALSA client number, else a client name), each with its `inputs` and `outputs` (raw port names), its `fingerprint`, exactly an OSD 0.6 fingerprint (`via: native`; `usb`, `ports` as lower-case words with no client or port numbers and no repeated words, `identity_reply`, `sends`, `controls` of 32 distinct entries at most, a field the device does not give being absent), and `measured`, a sibling object holding the local measures (`identity_reply_ms` with `identity_reply_port`, `periods_ms` with `periods_port`, the port each was measured on), never inside the fingerprint. A port of the system that is no device (the ALSA "Midi Through" kernel client) is left out: no fingerprint, no `next_step`. `detect::is_system_port(label)` recognises it by its client name (the label before the colon), case-insensitively whatever numbers follow; `detect::is_system_unit(unit)` is true for a unit whose every port is one. A device a driver recognises carries `driver` (`id`, `name`, and, when the service gives them, `confirmations`, `disputed`, `state`, `state_label`) and no `next_step`: the service's first candidate when linked (it is asked to match each device's ports and identity reply), else the local catalogue's. The request carries, per port, `usb: {vendor_id, product_id}` (numbers) when the ids were read, and no `usb` field otherwise. A driver with `state: "confirming"` is being confirmed (too few confirmations, or `disputed: true` when several devices are named): it is shown as such, never imposed. When the service has a catalogue candidate for a port, that candidate is the only answer; only with none, the devices it names without a card (`unlisted`: `vendor`, `model`, `firmware`, `confirmations`, `disputed`, `state`, `state_label`) are all returned in `unlisted` (also on the `detect` report and in the command's text, as `unlisted:` lines; the catalogue candidates of `detect` carry `state` and `state_label` too), and the `next_step` says to ask the person to confirm, not to name the device again; nothing is sent to the device on its account without the person's consent (`held_back` is unchanged). A device nobody recognises, and the service names none, carries `next_step`, a text (also in the result's text) saying to ask the person for its vendor, model and firmware (the firmware proposed from its identity reply when that carries a version), then map its controls with `report_mapping`, `device` being its vendor and model as the person gave them (« maker model »), and to send a first driver with `submit_driver`; linked and answered, it says neither the local catalogue nor SynthHub knows it; offline, or linked with no answer, it says only the local catalogue was looked at. When the service did not answer, the result's `notice` says so and the learn mode still reports. `mcp::learn_service_matches(server, learned)` asks the service and never fails, returning `mcp::ServiceMatches` (`NotLinked`, `Unreachable`, or `Answered` with, for each device in order, the service's catalogue candidates, else its devices without a card); `mcp::learn_report(learned, catalogue, listen, service, order)` builds the result without MIDI from those matches, for the MCP tool and the CLI alike. `detect::learn_units(units, listen)` learns only the units it is given, the ports of the system left out (`learn_all` learns every device). The `detect` command's `--learn` returns the same, printed for the terminal. Without `learn`, each port receives the universal Identity Request and nothing else without consent, whatever designates the port (its USB id, its name); every maker request may be a load for another device, so it is held back and each device lists it in `held_back` (hex requests; absent when none). `consent_ports` (a list of port names or `out_port` indexes; the agent must have asked the person) adds every maker request to those ports only: a fragment naming several ports or none is refused, naming them, and nothing is sent; a consented port has no `held_back`. The `detect` command takes the same through `--consent <port>`, repeatable.

**Sharing a fingerprint.** In learn mode, `share_fingerprint` (a part of one port's name; the agent must have asked the person; naming the device is the act that sends it) with `vendor`, `model` and `firmware` (the maker, the model and the firmware version the person gives; none empty, and a missing one is refused before anything is sent, every missing one named, in the words of the command or of the tool; the port must name exactly one device) send that device's fingerprint to the service's `POST /v1/fingerprints`; the `detect` command takes `--share-fingerprint` with `--vendor`, `--model` and `--firmware`. The learn report of a device nobody knows carries a `next_step` that asks for the three, and `proposed_firmware` when its identity reply carries a version, for the person to confirm; after a share the next step gives `report_mapping` the device as the person declared it, « maker model » (spaces reduced to one; the model alone when it already starts with the maker as a whole word, case ignored), the form the service accepts for a device without a card, never a slug; a device with a card keeps its catalogue id. What is sent: `device` (`vendor`, `model`, `firmware`), `usb` (`vendor_id`, `product_id`), `identity_reply`, `ports`, `sends` and `controls`; never the USB serial number, the host name, the measures or anything about the person. The tool's description and the command's help say these fields, and the result repeats what was sent. Nothing is sent for a private device (`Settings::covers` the `vendor/model` id), when offline, or when the copy is not linked, and the result says why; no consent is asked or kept, and nothing is written to `settings.toml`. The result carries `sharing`, a text saying what happened; a failure of the service (offline, HTTP error, 429) leaves the fingerprint on the machine, with no retry, is said in that text and on the standard error, and the detection goes on. The type sent mirrors what the service reads today and moves to `synthhub-protocol` when that crate exists. `mcp::device_id(vendor, model)` is the id `vendor/model`, each slugged, of a device the catalogue does not describe; `mcp::shared_next_step(vendor, model)` is the text of the next step after a share, giving `report_mapping` the declared « maker model » as `device` (the firmware is no part of it); the private list covers a `report_mapping` call named so when its slug matches, under any cut of the words into maker and model; `mcp::refusal_in_words(said, command)` rewrites a service refusal that names `vendor`, `model` or `firmware` in the words of the command typed (`--vendor`) when `command`, and returns any other text as it is. `mcp::probes_json` writes the service's answer to `GET /v1/detect`: for each probe `request_hex` and `ports`, and, only when the identity has them, `usb` (a list of `{vendor_id, product_id}`) and `match_ports` (the port names of the identity); each key is written for itself, and `Online::probes` reads back the same probes, an absent key as an empty list. A probe without them is held back, so a linked copy without them sends only the universal request unless consent is given.

**What leaves without consent.** The universal Identity Request leaves on every port. No maker request leaves without consent, whatever designates the port (its USB id, its name or nothing): the proof of a device is no proof that the bytes of a card only read (`recognition::send_plan`). The request held back is listed in `held_back` for that port, with the way to consent (`--consent`, `consent_ports`), which sends it. `usb` and `match_ports` stay read by the recognition (`by_usb`, `by_port` proofs), never by a send. A maker request received from the service (`Online::probes`) that is not one SysEx message (it starts with F0, ends with F7, holds no status byte between, at most 32 bytes: `recognition::maker_request_fault`) is refused with its cause, with or without consent.

`export_device` writes one driver in a format of `osd-formats` and only reads. `install_export` (`device`, `on`, `confirm_overwrite`) is the tool that puts an export on a plugged device, the only one of the two that writes: the format, the path and the way come from the target's descriptor, nothing names a device, and without `confirm_overwrite: true` nothing is sent and the preview (format, way, path, size, losses) is returned. The library publishes `osc_bridge::install::install` (the gesture) and `osc_bridge::export::Format`, which wraps the `osd-formats` format.

**The opening of the MIDI system.** One place opens it, through one guard. `midi_port::guarded_open(open)` runs an opening closure and returns its value; a failure, or a panic inside the MIDI library (midir panics when ALSA cannot allocate a queue, a failure the application cannot prevent: a written departure from the reference, which returns `InitError`), comes back as an error naming the MIDI system and the cause. `midi_port::Opener` is the type of what a command takes its MIDI from (a function returning the opened `Midi`); `midi_port::open_hardware` is the default opener, the machine's hardware through the guard. `install::install_command(source, target, confirm_overwrite, open)` is the `export --on` command, taking its MIDI from `open`; `mcp::serve_with_midi(opts, base, cache, input, out, open)` is `mcp::serve` with the opener the MIDI tools (`take_sound`, `load_preset`, `install_export`) use. Tests give these the shared fake hardware.

Three tools link devices of a running orchestrator, reached by its UDP address (`target`, else `--default-target`) through its control addresses, and answering with the orchestrator's replies, or saying that none answered:

| Tool | Does | Orchestrator address |
|---|---|---|
| `add_link` | links `from` to `to`, optionally scaling the first argument (`map`: input range, output range); effective at the next message; refused, naming the address or the chain, for an unknown device, an address its driver does not have, a loop or more than four hops | `/bridge/link/add` |
| `remove_link` | removes the link from `from` to `to`; refused, naming it, when it does not exist | `/bridge/link/remove` |
| `list_links` | lists the links of the configuration file and those added live, each with source, target, origin (`file` or `live`) and scaling | `/bridge/link/list` |

### One answer per device

The `detect` report and `detect_hardware` (without `learn`) return one element per device: the ports sharing an ALSA client number (else a client name) are one device, as in the learn mode. An element lists `ports`, each `{port, out_port, in_port}` in the order of the system; its `port`, `out_port`, `in_port` and `run_command` (`--out-port`, `--in-port`) are those of the port that gave the strong proof, else the first. The candidates are computed over all the ports by one formula: a strong proof on one port beats the name alone of the others, and a device with a strong proof lists no candidate resting on a name only. The command prints `port N of <client>` for a device of several ports. `detect::group_probed(found)` is the grouping.

### The proofs of a detection

A candidate of `detect`, of the learn mode and of `detect_hardware` carries `proofs`, a list of `{nature, kind}` (in `detect` each also names the `port` that gave it) (it replaces `recognised_by`, removed), also printed as "because: …". The library publishes `recognition::Nature` (`Strong`, `Medium`, `Weak`) and `recognition::Proof` (`nature`, `kind`). `score` stays the ranking weight of a candidate; it is no probability.

**The order of two cards of one device is a value the caller gives.** `recognition::TierOrder` is `fn(&str) -> u8` (a rank per source tier, lower first; no state, `Send + Sync`, `'static`); the library knows no tier. `DeviceIndex::build(dir, order)`, `recognition::rank(…, order)`, `mcp::learn_report(…, order)` and `McpOptions.tier_order` receive it from their caller. `synthub::catalogue::tier_rank` is the order of the catalogue's tiers (unknown tier: 7) that the application and the integration tests give.

| Nature | Kinds | What it allows |
|---|---|---|
| strong | `identity reply` (recognised by the card), `usb id` (declared by the card); the service's confirmed fingerprint | the device is "recognised"; a run command is proposed when no rival holds a strong proof too (two rivals: no command, both shown with their proofs) |
| medium | `maker` (the maker of the identity reply) | the candidate is shown with its proof; no recognition by itself |
| weak | `name` | at most "possible, to confirm" (`state: "possible"`), no run command, never the answer of a port |

A name made only of common words (synth, control, controller, audio, midi, mini, interface, port, input, output) is no proof. A port with no proof other than the name and no candidate left is "unknown": the next step is the learn mode's. A software port never receives the card of a real device. A device the service names "being confirmed" is printed as the service's answer, "to confirm", with no run command.

## The OSC addresses

Each device's addresses come from its driver, under its prefix; the uniform addresses (`/identity`, `/program/recall`, `/program/dump`) are the same on every device; `/bridge/status` and `/bridge/docs` describe the bridge itself. An orchestrator also answers, to any client (UDP or WebSocket), `/bridge/link/add <from> <to> [in_lo in_hi out_lo out_hi]` (`/bridge/link/added`, or `/bridge/link/error <text>`), `/bridge/link/remove <from> <to>` (`/bridge/link/removed`, or `/bridge/link/error <text>`) and `/bridge/link/list` (one `/bridge/link/list/item <from> <to> <origin> [scaling]` per link, then `/bridge/link/list/end <count>`). A link follows the output of another link: with a→b and b→c, a message received at a reaches c, once per device address. A chain is followed for four links; a matching fifth link is not followed, and the cut is said by `/bridge/link/error` naming the chain followed. OSCQuery publishes the whole namespace.

The faults of a message come back to whoever sent it. A message that cannot be built, run or queued (a command or parameter whose frame does not build, a script that fails, an unknown address, a full emission queue) is answered, to its sender alone, `/bridge/fault <address> <reason>` (two strings: the message's address and why). A fault whose message has no real sender (re-injected by a link, set off by an incoming MIDI message, a MIDI port that refuses a frame) is broadcast to the declared clients, as `/bridge/status` is. A correct message answers nothing. A sender that wants to know its message is handled asks for it, in the same packet: `/bridge/sync <id>` is answered `/bridge/done <id>` once what precedes it in the packet is handled, after any `/bridge/fault`; nothing is answered to a sender that does not ask. Over WebSocket the answer goes through the WebSocket broadcast. The Rust door: `runtime::ReplyTo` (the route back to a sender, beside `SendOsc`), `runtime::dispatch_packet_to_device(state, packet, send_osc, reply_to, from)` (one packet, its `/bridge/sync` answered after the lot), and `reply_to` beside `send_osc` in `dispatch_to_device`, `dispatch_osc_to_device` and `BenchPath::dispatch`.

## The time the core adds

The core adds under 1 ms to a message, MIDI excluded (the charter's bound). The night bench `tests/it_budget/orchestrator_message_time.rs` holds it with two measures, each judging the median and the worst case: a message that follows a link (`message_that_follows_a_link_adds_under_the_bound`) and a message that follows no link (`message_that_follows_no_link_adds_under_the_bound`). They run on a loaded MIDI device without a port, from the message entering the orchestrator to the frame reaching the device's emission queue; the OSC wire encoding, the socket and the MIDI driver stay outside.

## The Lua a driver declares

A command `script` sees, besides `ctx` and `ob`, Electra One's two APIs under Electra's names (<https://docs.electra.one/developers/luaext.html>), so a preset's function runs unchanged:

- `parameterMap.get(deviceId, PT_<TYPE>, number)` answers the value held for the command whose `_electra.parameter` is (type, number): last sent or received, else its default, else the low end of its range, else 0.
- `devices.get(deviceId):getChannel()` answers the channel the engine sends the driver on, 1..16.

## The faults

- `NoDriver` — no driver matches the name, in the cache or the service.
- `Unauthorized` — an MCP request over HTTP without the right token.
- `ConsentRefused` — the person refused a message at the door.
- `DeviceFault` — a device description that cannot be used as written (device, field, cause), held by the loaded device and read by `lint` and `inspect`; `mcp::fault_blocks(faults)` turns the faults of the identities `detect_hardware` set aside into one text block each, without MIDI.
- the faults of `synth-core`, `synth-io` and `synthhub-protocol`, passed on with their code.
